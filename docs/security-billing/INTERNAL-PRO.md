## Resulting behavior

`internal_test_entitlements` is a separate private relation with a primary key and CHECK restricted to that exact UUID and purpose `owner_internal_testing`. It references the existing Auth user; it creates no Auth account. The proposal seeds one owner-approved grant, initially without an arbitrary expiration. It remains valid until privileged revocation, deletion or an explicitly configured expiry. No Stripe ID, price, status, sync timestamp, webhook ledger or purchase analytics record is generated by this grant.

The table has RLS enabled and no client policy or table privileges. Public/anon/authenticated cannot invoke its lookup RPC. Service role can SELECT/UPDATE the row and execute its SECURITY INVOKER lookup; inserting/removing grants requires the migration/database administrator. Both the SQL lookup and the server-only helper independently pin the same UUID. A missing, expired or revoked grant returns false; lookup errors fail closed.

Verified owner requests with a valid grant skip canonical Stripe refresh, so the owner's historical fabricated billing IDs do not block practice. SQL admission and AI authorization recognize the grant as Pro, retain the ordinary paid-session lease, and still enforce budgets and recording/session ownership. Internal access is explicitly returned as `entitlementSource: internal_test`; free and verified Stripe access remain distinct. Other users take the unchanged Stripe path.

Settings labels the entitlement as internal test Pro and omits Stripe billing controls. Both checkout and portal independently reject internal-test billing creation after verified authentication, before any Stripe API call. The grant does not fabricate a subscription or allow a caller to assume another user's identity. Existing authentic paid subscriptions continue through the ordinary synchronization/webhook contract.

## Revoke, restore and operational rollback

The following are review examples, not applied SQL. First record the complete grant before-image in the restricted operational record. For an explicitly approved owner-grant revocation, privileged code/operator can run:

```sql
UPDATE public.internal_test_entitlements
SET revoked_at=clock_timestamp()
WHERE user_id='dc869fa0-8652-4df1-bede-93a776ed70eb'::uuid
  AND revoked_at IS NULL
RETURNING user_id,purpose,granted_at,expires_at,revoked_at;
```

Require the expected one-row result and verify the subsequent lookup returns false. Revocation restores ordinary Stripe/free admission without erasing historical usage or changing subscriptions. Previously admitted sessions retain the ordinary bounded processing lease; revocation does not silently delete their work. If an unresolved fabricated binding is still present, ordinary refresh can return its existing Stripe error: grant revocation does not automatically repair or quarantine it.

For an explicitly approved restoration, restore only this owner's exact captured grant fields, including its intended expiration and revocation state. Do not clear revocation globally, invent a Stripe status or replay checkout. For approved quarantine rollback, restore the complete archived binding only after verifying its exact row ID/user/customer/subscription and absence of conflicting canonical rows. A reintroduced fabricated binding still requires internal access to avoid its original refresh error; it does not become real Stripe data.

For a failed code/schema cutover, keep maintenance active and follow `ROLLOUT.md`. Preserve the grant/usage/billing/outbox records while coordinating matching code and SQL.
